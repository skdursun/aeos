# AEOS Remember Command Implementation Plan

## Purpose
Define the implementation path for the first AEOS memory CLI command:
`aeos remember`.

This plan describes how user input becomes a validated memory entry and is then
prepared for a stored memory artifact while preserving the boundary:

CLI -> core -> memory -> future storage

## Remember Command Goal
`aeos remember` should let a user explicitly capture one durable project memory
entry from terminal input.

The MVP should prove:
- command input can be collected without a CLI framework;
- memory type, title, summary, tags, source task, and sections can be normalized;
- the normalized request can become a core `MemoryEntry`;
- validation runs before Markdown generation;
- Markdown output is produced through `@aeos/memory`;
- writer preparation returns a destination path and content without search
  integration.

## Non-goals
- Do not implement memory search.
- Do not implement audit writing.
- Do not implement verification reporting.
- Do not add embeddings, vector storage, or external memory services.
- Do not add dependencies.
- Do not choose a CLI framework.
- Do not choose a permanent storage backend.
- Do not infer memory facts from raw conversations.
- Do not write to `brain/` without an explicit remember command path.
- Do not change the existing memory schema unless a later task explicitly scopes
  that work.

## Current Memory Foundation Status
- `packages/core/src/memory.ts` defines shared memory contracts, including
  `MemoryType`, `MemoryEntry`, `MemoryWriteRequest`, and validation result
  shapes.
- `packages/memory/src/validation.ts` validates complete `MemoryEntry` objects
  and delegates frontmatter checks to `@aeos/core`.
- `packages/memory/src/markdown-entry.ts` serializes a valid `MemoryEntry` into
  Markdown with YAML frontmatter.
- `packages/memory/src/writer.ts` prepares write requests and write results,
  including deterministic file paths and Markdown content.
- `apps/cli/src/commands.ts` already uses plain `process.argv` dispatch and
  compact stdout/stderr handling for existing commands.
- Existing CLI JSON commands establish a pattern for future structured output,
  but JSON support is not required in the first remember implementation.

## Command UX Design
MVP examples:

```sh
aeos remember
aeos remember --type decision --title "Example"
aeos remember --json
```

Default human output should be compact:

```text
Memory: prepared
Type: decision
Title: Example
Path: brain/decision/2026-07-31-decision-example-<id>.md
Status: draft
```

Validation failure output should be stable:

```text
Memory: fail
- title: Memory title is required.
```

## Input Sources
The command should support these sources in order:
- interactive prompts for `aeos remember`;
- flags for typed invocation, such as `--type` and `--title`;
- later stdin support for body text if scoped by a future task;
- later JSON input/output through `--json`.

The MVP should not parse arbitrary free-form conversations. If required fields
are missing in non-interactive mode, the command should return a usage error.

## Memory Type Selection
Supported types come from the public core `MemoryType` union:
- `bug`
- `decision`
- `pattern`
- `incident`
- `lesson`
- `prompt`
- `benchmark`
- `research`
- `postmortem`

Interactive mode should ask for a type from the supported list. Typed mode
should require `--type <type>` unless a later task defines a documented default.
Invalid types should fail before constructing a memory entry.

## Required Fields
The command must collect or derive:
- `type`
- `title`
- `date`
- `sourceTask`
- `status`
- `tags`
- `summary`
- `sections`
- `redactionStatus`

MVP defaults:
- `date`: current ISO timestamp generated by the command layer.
- `sourceTask`: `unknown` unless `--source-task <id>` is supplied.
- `status`: `draft`.
- `tags`: empty list unless `--tag <tag>` is supplied.
- `redactionStatus`: `not_required` unless validation later blocks content.
- `sections`: at least one section from the captured body, using a predictable
  heading such as `Details`.

## Validation Flow
1. Parse CLI flags and interactive answers into a small remember input object.
2. Validate required CLI fields and allowed memory type before building core
   objects.
3. Normalize title, tags, source task, status, summary, and section content.
4. Build a `MemoryEntry` using `packages/core/src/memory.ts` contracts.
5. Call `validateMemoryEntry` from `@aeos/memory`.
6. Stop on validation failure and print stable issue lines.
7. Continue only when validation is valid.

## Markdown Generation Flow
1. Pass the validated `MemoryEntry` to `buildMemoryMarkdownEntry`.
2. Let `@aeos/memory` serialize frontmatter and body sections.
3. Keep Markdown formatting behavior out of `apps/cli`.
4. Return generated content only through the writer preparation flow.
5. Do not hand-build YAML or Markdown in the CLI.

## Writer Flow
1. Build a `MemoryWriteTarget` from the project memory root and selected
   collection path.
2. Call `createMemoryWriteRequest(entry, target)`.
3. Call `createMemoryWriteResult(request)` to receive destination path and
   content.
4. In the first implementation, either keep the result as a prepared artifact or
   perform a narrowly scoped local file write only when that task explicitly
   includes write behavior.
5. Refuse overwrites when file writing is introduced.

The CLI should not own durable storage policy. It should call the memory package
and report the result.

## Audit Integration Placeholder
Every successful remember result should contain enough data for a later audit
event:
- command name;
- memory type;
- title;
- destination path;
- validation status;
- created or prepared status.

No audit file should be written during this command MVP unless a later task
explicitly scopes audit integration.

## Verification Integration Placeholder
Validation results should remain usable as later verification evidence.

The command should keep issue codes and pass/fail status available internally so
future JSON output and verification reports can reuse the same result shape.

## CLI Error Handling
- Usage errors return exit code `1`.
- Validation failures return exit code `1`.
- Unexpected internal failures return exit code `2`.
- Normal output goes to stdout.
- Usage and unexpected errors go to stderr.
- Validation issue lists may go to stdout for consistency with existing task
  validation output.
- Error messages should be compact and stable for smoke checks.

## JSON Output Future Support
`aeos remember --json` is reserved for structured output.

Future JSON should include:
- `ok`
- `status`
- `reason`
- `type`
- `title`
- `path`
- `created`
- `issues`

The first remember implementation may reject `--json` with a documented
not-yet-supported error, or implement JSON output if explicitly scoped by that
task. The command contract should not require a redesign when JSON is added.

## MVP Scope
- Add command routing for `remember`.
- Collect typed `--type` and `--title` input.
- Add minimal interactive input for `aeos remember`.
- Normalize a complete `MemoryEntry`.
- Validate through `@aeos/memory`.
- Generate Markdown through `@aeos/memory`.
- Prepare a writer result through `@aeos/memory`.
- Print compact human-readable output.
- Add focused smoke verification.

## Later Scope
- JSON output.
- Stdin input.
- Rich interactive prompts.
- Additional typed flags for tags, source task, owner, confidence, related
  entries, and custom sections.
- Actual local file write if not included in the first core flow task.
- Audit event emission.
- Verification evidence emission.
- Search indexing or search command integration.
- Storage backend decision.

## Stop Conditions Before Search Integration
- `aeos remember --type decision --title "Example"` can produce a validated
  prepared memory artifact.
- `aeos remember` has a defined interactive flow or a clearly documented MVP
  limitation.
- Validation failures are stable and visible.
- Markdown generation is delegated to `@aeos/memory`.
- Writer preparation is delegated to `@aeos/memory`.
- The CLI does not contain schema, Markdown, or storage policy beyond command
  parsing and output formatting.
- No new dependencies or CLI framework have been added.
- JSON output has a reserved contract or implemented shape.
- No search command depends on remember output until the write path and output
  behavior have been reviewed.
